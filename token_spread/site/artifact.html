What is a GPU-hour worth in tokens?

A GPU-hour has a market rental price. It also has a value as a factory for tokens: run an open-weight model on it, sell the output at public API prices, and see what it earns. The gap between those two numbers is the token spread.

Reading these numbers

    Method

    How the spread is calculated

    Four public inputs, one multiplication chain. Each step is simple; the uncertainty lives in the inputs.

    Input · OpenRouterAPI price per million tokensSeparate input and output prices for each provider serving the model.
    StepBlended priceWeight input and output prices by the traffic mix, e.g. 3 input tokens per output token.
    Input · InferenceXThroughput per GPUTokens per second one GPU processes at the chosen speed-per-user floor.
    StepTokens per GPU-hourThroughput × 3,600 seconds × utilization.
    ResultImplied revenue per GPU-hourTokens per hour ÷ 1,000,000 × blended price.
    Input · Silicon DataRental price per GPU-hourNeocloud on-demand index, the basis of CME's GPU futures.
    ResultToken spread and ratioRevenue minus rental, and revenue divided by rental.
    # r = input tokens per output token blended_price_per_Mtok = (r × input_price + output_price) / (r + 1) tokens_per_gpu_hour = throughput_tok_s_per_gpu × 3600 × utilization implied_revenue_per_gpu_hour = tokens_per_gpu_hour / 1,000,000 × blended_price_per_Mtok token_spread = implied_revenue_per_gpu_hour − rental_price_per_gpu_hour spread_ratio = implied_revenue_per_gpu_hour ÷ rental_price_per_gpu_hour breakeven_utilization = rental_price ÷ (revenue at 100% utilization)

    Concepts

    Token
    The unit LLMs read and write, roughly ¾ of an English word. APIs charge per million tokens.
    Input vs output tokens
    Input (prompt) tokens are processed in parallel and are cheap to serve. Output tokens are generated one at a time and cost more, so providers price them 2–6× higher.
    Blended price
    One price per million tokens that mixes input and output prices in the proportions real traffic has. Chat and coding traffic is input-heavy, often 3:1 to 10:1.
    Open-weight model
    A model whose weights are published, so anyone can serve it and anyone can benchmark it. Closed models hide their hardware, so they are left out.
    Dense vs mixture-of-experts (MoE)
    A dense model uses all its weights for every token. An MoE model routes each token through a few "experts", so a 397B-parameter model may only use 17B per token, which makes it cheaper to run than its size suggests.
    Throughput per GPU
    Total tokens (input + output) a GPU processes per second, divided across every GPU in the serving setup.
    Speed per user (interactivity)
    Output tokens per second one user sees streaming back. Below roughly 20–30 tokens/s a chat feels slow.
    Concurrency and the operating point
    Serving more requests at once raises throughput per GPU but slows each stream. The operating point is where on that trade-off curve you run. We take the highest-throughput point that keeps each user above the speed floor.
    Utilization
    The share of paid hours spent serving at that operating point. Real fleets idle at night and keep headroom for traffic spikes.
    Precision (bf16, fp8, fp4)
    How many bits each weight uses. Fewer bits mean more throughput but can cost a little quality. B200 has hardware fp4 support; H100 does not.
    Speculative decoding (MTP)
    A small draft model or extra prediction heads guess several tokens ahead, and the main model verifies them in one pass. Common in production, and it raises throughput at a given speed per user.
    Disaggregated, multi-node serving
    Splitting prompt processing and token generation onto different GPUs, sometimes across machines. Needed for very large models such as DeepSeek-R1 on H100.
    GPU rental index
    Silicon Data publishes daily H100 (SDH100RT) and B200 (SDB200RT) on-demand rental indices from neoclouds. CME launched cash-settled futures on them (GPU1, GPU2) on 5 October 2026.
    Owner TCO
    What a GPU-hour costs someone who owns the hardware at hyperscaler scale: depreciation, power, hosting. SemiAnalysis estimates this for InferenceX. It is a floor under rental prices.
    Token spread and spread ratio
    Spread = implied revenue − rental, in dollars per GPU-hour. Ratio = revenue ÷ rental. A ratio of 2× means a GPU-hour earns twice its rent at list API prices.
    Breakeven throughput
    Tokens per second one GPU must produce for a model's price to cover the GPU's rent at a given utilization: rent ÷ (3,600 × utilization × price per token). For open-weight models, measured throughput ÷ breakeven throughput = spread ratio.
    Closed vs open-weight
    Closed models (Claude, GPT, Grok) are only available through their makers' APIs and cloud partners. Their size, hardware and throughput are not published, so only their prices enter this analysis.
    Breakeven utilization
    The utilization at which revenue equals rent. Above 100% means the model cannot pay its rent on that GPU at market prices, however busy it is.

    Caveats

    Gaps, uncertainties, and what would fix them

    Data gaps in this build

      Biggest uncertainties

      • Which point on the throughput curve. Dropping the speed floor can double throughput per GPU. Benchmarks use random data at fixed lengths; production traffic has prefix-cache hits, bursts and long-context tails.
      • Configurations differ across GPUs. The best published point may use speculative decoding on one GPU and not the other, or multi-node serving. Part of the B200 advantage may be better-tuned software, not silicon.
      • Stale benchmarks. Some model and GPU pairs have not been re-run for months; inference software improves fast, so their throughput is likely understated.
      • Unmeasured mixes. 3:1 is interpolated between the measured 1:1 and 8:1 points; 10:1 is held at 8:1.
      • List prices and on-demand rents. OpenRouter shows public per-token prices without volume or cache discounts. Rental is the neocloud on-demand index; term contracts are cheaper.
      • Closed models are price-only. Their breakeven throughput is exact arithmetic, but nothing here says what throughput they actually reach or on which hardware.
      • Revenue is not margin. The spread leaves out CPU hosts, networking, storage, staff, idle peak capacity and the API marketplace's fee.

      What would most improve v1

      • Production throughput from providers' own disclosures, or OpenRouter's measured throughput per endpoint.
      • Matched benchmark configurations across GPUs, plus a measured 3:1 sequence.
      • Rental index history and term prices, to backfill the time series and compare on-demand with reserved capacity.
      • Which hardware each provider runs, so each provider's spread uses its real GPU.
      • A small model (8B class) and the newest MoE models once H100 benchmarks exist for them.
